## 2. ТЗ

### R9. Карточка «Данные» растягивается на всю ширину и высоту левой панели

**Текущее состояние**: `inner` — окно внутри `left_canvas`; в `_left_scroll_state` (graphlab_app.py:458-471) при `<Configure>` canvas выполняется только `itemconfigure(win_id, width=...)`. Карточка создаётся в :474 как `self._card(inner, "Данные", row=0)` (stretch=False → sticky="ew").

**Требования**:
1. R9.1. Добавить `inner.columnconfigure(0, weight=1)` — карточка занимает всю ширину панели (за вычетом скроллбара).
2. R9.2. Создавать карточку «Данные» с `stretch=True` (sticky="nsew", строка 0 в `inner` получает weight=1) — при наличии свободного вертикального места карточка растягивается до нижнего края панели.
3. R9.3. В `_left_scroll_state`: если контент помещается в canvas (`content_h <= view_h`) — дополнительно `left_canvas.itemconfigure(win_id, height=view_h)`; при переполнении — естественная высота (`height=0`). Автоскрытие скроллбара (R6.2) не меняется.

**Критерии приёмки**:
- При 1–3 линиях: ширина карточки = ширина панели (свободного места справа нет), нижний край карточки упирается в низ панели, вертикальный скроллбар скрыт.
- При переполнении (много линий): карточка на всю ширину, естественная высота, вертикальный скроллбар появляется, прокрутка вверх/вниз работает (R6.2/R7.4 не нарушены).
- При ресайзе окна ширина карточки обновляется сразу (через `<Configure>` canvas), полей не обрезает.

### R14. Бокс «Данные» не двигается колесиком, когда контент помещается (устранение рассинхронизации скролл-состояния)

> Источник: сообщение пользователя в текущей сессии — баг: при старте с одной линией, после добавления второй или после удаления всех линий бокс «Данные» не зафиксирован и ходит колесиком вверх/вниз; при трёх линиях фиксация есть. В полноэкранном режиме, когда бокс не заполнен данными до конца, бокс тоже свободно двигается колесиком.

**Диагностика (замеры скриптами-пробниками, v1.0.5a):**
- В устойчивых состояниях (после усадки layout) при 2000×900 / 1600×900 / 1920×1080 все «помещающиеся» состояния (1–3 линии, req_h 262/363/464 ≤ view_h 505–685) зафиксированы — колесико не двигает; при minsize 1024×576 (canvas всего 447×181) всё переполняется и скроллится — корректно по R12.
- Захвачено промежуточное **рассинхронизированное** состояние: `item_h=365` + `scrollregion=''` (значения ветки «помещается») при **mapped vbar** (значение ветки «переполнение») → `yview_scroll` сдвинул позицию 0.0→0.213, т.е. бокс скроллится, хотя контент помещается.
- Причина: `_update_left_scroll` (graphlab_app.py:572-599) вызывается несколько раз за одно изменение layout (несколько `<Configure>` + явные вызовы из `add_line` :606 и `LineRow._remove` :200), и три связанные величины — видимость vbar, высота item, scrollregion — могут остаться вразнобой. Явный вызов читает `inner.winfo_reqheight()` до усадки layout (устаревшее значение → неверная ветка), а исправляющего `<Configure>` после этого не наступает (выделение `inner` не меняется). Переход «переполнение» → «помещается» не сбрасывает позицию прокрутки (yview).

**Требования:**
1. R14.1. Атомарность состояния: в `_update_left_scroll` все три величины (видимость vbar, `itemconfigure(win_id, height=...)`, `scrollregion`) выставляются за один проход по одному вычисленному режиму; после выставления — контроль согласованности: в режиме «помещается» scrollregion пуст и `yview() == (0.0, 1.0)`, при несовпадении — повторный вызов через `after(0)` (не более одного повтора).
2. R14.2. Отложенная пересборка: явные вызовы из `add_line` (graphlab_app.py:606) и `LineRow._remove` (graphlab_app.py:200) выполняются после усадки layout — `self.left_canvas.after(0, self._update_left_scroll)` — чтобы `winfo_reqheight()` читалось по готовой геометрии.
3. R14.3. Сброс при смене режима: переход «переполнение» → «помещается» сбрасывает позицию прокрутки (`yview_moveto(0.0)`) и очищает scrollregion; в режиме «помещается» скролл-диапазон отсутствует полностью.
4. R14.4. Страж в `_on_mousewheel` (graphlab_app.py:912-942): для зоны левой колонки перед `yview_scroll` проверять, что диапазон реально существует (высота `bbox("all")` больше высоты canvas); если нет — не прокручивать (return 'break'). Страж страхует от любых остаточных рассинхронизаций.

**Критерии приёмки:**
- Старт с одной линией: колесико над боксом «Данные» — бокс и его содержимое не двигаются.
- Добавлена вторая линия (контент помещается) — не двигается; все линии удалены — не двигается.
- Три линии — фиксация, как ранее.
- Полноэкранный режим, бокс не заполнен данными до конца — колесико не двигает бокс.
- Переполнение (13+ линий): колесико и скроллбар прокручивают содержимое внутри бокса (R12 сохранён); после удаления линий до «помещается» прокрутка отключена.
- Быстрые последовательные добавления/удаления линий (5–10 операций подряд) — без остаточного состояния: vbar, высота item и scrollregion согласованы, колесико ведёт себя по фактическому контенту.

3. Ресайз окна в обе стороны: зазор не появляется, скролл-состояние переключается корректно.
4. Сценарий пользователя (R14): старт с одной линией → колесико; добавить вторую → колесико; удалить все → колесико; довести до трёх линий → колесико — в «помещающихся» состояниях движения нет.
5. Полноэкранный режим, бокс не заполнен данными до конца → колесико — движения нет (R14).
6. Быстрые добавления/удаления линий (10+ операций подряд) → проверка согласованности vbar / scrollregion / высоты item и поведения колесика (R14).

### Решения по открытым вопросам

1. **Ширина** — 2000 px (верх запрошенного диапазона +300…+400 px); если предпочтительнее 1900 — меняется одна строка (graphlab_app.py:205).
2. **Механизм скролла** — сохраняется существующий canvas+scrollbar из R6 (а не Listbox со своим бегунком): меньше изменений, колесико мыши и автоскрытие бегунка работают без переделки.
3. **Почему «1–2 линии ходят, а 3 — зафиксирована»** — в устойчивых состояниях это разделение не воспроизводится (при больших окнах все «помещающиеся» состояния зафиксированы; при minsize всё переполняется); симптом — переходная рассинхронизация `_update_left_scroll` во время layout-изменений. Поэтому R14 целится в механизм (атомарность, отложенный пересчёт, страж колесика), а не в конкретную геометрию окна.
4. **Механизм отложенного пересчёта** — `after(0)` на canvas: один проход event loop, к моменту выполнения layout уже устоялся; искусственных задержек (timeout > 0) не вводится.
